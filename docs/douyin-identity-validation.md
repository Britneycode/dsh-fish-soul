# 抖音会话身份验证：阻断项与验收清单

本 PR **不启用**抖音私信/群聊处理或出站发送。下列步骤是恢复前的验收要求，不是已实现的身份绑定方案。当前抓包缓存以昵称索引，读取接口时可能混入其他会话；页面昵称、用户头像、消息中的昵称和独立出现的 senderId 都不能作为授权或收件人证据。

## 安全数据边界

- 真实环境测试必须使用经参与者同意的测试账号，且只能由设备拥有者在自己的设备上操作。不要发送真实私信内容、Cookie、令牌、二维码、登录态、浏览器 profile、完整网络抓包或未经同意的用户标识。
- 测试记录只需要版本、系统、场景及通过/失败；需要比较标识时在本地用每次试验独立的随机别名表示相等关系，不提交原始 ID，也不将随机别名作为正式身份绑定凭证。
- 不直接在生产账号解封私信，不通过篡改浏览器或平台安全策略来规避限制。

## 需要证明的事实

1. 平台数据能否独立确认当前打开的**会话 ID**，并且将响应、发送者和当前会话绑定在一起？需要证明并发请求、历史缓存、重载和切换会话时不会将另一会话的结果误认为当前会话。字段名相同或消息恰好包含同一个 ID 不能证明这一点。
2. 私聊中能否区分自己和对方的稳定 ID？更名、重启、重新登录之后是否一致？ID 的来源、作用域、有效期和处理失败语义是什么？
3. 目标会话在发送动作期间能否保持一致，并在每段文字、图片、表情的最终提交前校验？窗口切换、同名、DOM 变化或缺失证据时必须停止；读回只能作为结果证据，不能替代发送前的目标验证。
4. 接口数据是否适用于项目使用的普通抖音账号？小程序 OpenAPI 的 OpenID 有应用作用域，不能直接当成现有网页 senderId 或假定与其一一映射。小程序私信能力需要相应资质与授权，必须单独评估。

## 必测矩阵（先实现可信证据再执行）

| 场景 | 通过条件 |
| --- | --- |
| 两个不同账号使用相同昵称 | 非绑定者不能获得主人权限、访问主人记忆、合并 QQ 会话或收到主人私信 |
| 主人改名、昵称回滚 | 仅可信稳定身份一致时保持绑定；不能通过旧昵称自动迁移 |
| 切会话时收到其他会话的异步响应 | 不把响应写入当前会话；身份不明则隔离 |
| 缓存、断网、登录切换、重启、页面变更 | 缺少验证证据时停止处理和发送，不能回退到昵称信任 |
| 多段发送途中切换会话或验证失效 | 未验证的后续段不发送；已发送与不确定结果分别记录，不自动重发 |
| 读取前后强制退出或断网 | 已记录的读取意图提示可能遗漏；不得声称已找回抖音端消息 |
| 旧的昵称、QQ 对照和记忆 | 原样保留但不自动赋权；任何迁移必须由用户核实并具备可撤销、审计和冲突处理 |
| 主人、普通联系人、群聊 | 工具权限、记忆、共享会话和出站路由使用一致的验证结果，未知身份默认拒绝 |

完成真实页面和宿主测试后，PR 仍需审查具体绑定流程、冲突/撤销机制、发送过程中的竞态及配置兼容性，才能考虑解除安全暂停。
